Council review: Tome, the containment-cell coding harness

An adversarial multi-expert assessment of the repository at zwaneldmz/tome — a Rust + Tauri v2 desktop app that runs AI coding agents in an OS sandbox with a provider-only network proxy. Five specialists: security, architecture, quality & testing, performance, and documentation consistency.

7.6/10

Verdict: an unusually thoughtful security design and strong docs/process, held back by three things that must land before it can be trusted as a security product: the security/perf docs still describe the removed Electron code, Linux is network-contained but not file-confined, and there is no macOS Rust gate in CI.

executive summary

What the council thinks

Tome is a serious, security-first take on a crowded category. Its strongest ideas — widen the proxy, never the sandbox, second-factor pane unlock, a SHA-1-pinned repo allowlist with TOCTOU-safe re-consent, and a confused-deputy-bounded conductor — are genuinely better than most agent harnesses. The engineering is disciplined: 46.5k LOC, a clean renderer/shared/Rust split, 282 JS + 798 Rust tests, an audit gate with reviewed exceptions, and a real (if narrow) Linux proof job. The gaps are not design gaps so much as reconciliation and release gaps.

Top 5 actions, in order

  • crit Rewrite SECURITY.md, docs/THREATMODEL.md and docs/perf.md for the Tauri code — they still cite src/main/, node-pty, electron-vite and sandbox:true.
  • high Implement Landlock file confinement on Linux (today it is egress-only — TODO(landlock)), or soften the "containment cell" claim.
  • high Add a macOS cargo test gate to build.yml; the 798 Rust tests and the seatbelt paths are not exercised on the primary CI platform.
  • high Wire Apple Developer ID signing + notarization into the release pipeline.
  • med Add a DOM/end-to-end smoke test for layout restore + pane spawn — a shipped regression (restore was a silent no-op) is exactly what this catches.

expert 01

🔒 Security engineer

Rating: 8.0 / 10 — design excellent, one material platform gap.

The threat model is the strongest part of this project. The core invariants are load-bearing and mostly well-reasoned.

What's strong

  • Fail-closed lock gate. Every IPC handler refuses while locked except an explicit pre-login allowlist, with slug-shaped key vetting and reserved keys (egress, egress-auth) unreachable.
  • Widen the proxy, never the sandbox. The seatbelt profile is fixed at spawn; unlocking only widens the loopback proxy. This is the right primitive and it's stated precisely.
  • Second-factor pane unlock. Freeing a pane re-proves something (TOTP or passphrase) even though login already authenticated — correct for an egress-widening action.
  • Confused-deputy caps. The conductor loop is bounded (8 turns), scrollback is ANSI/control-stripped, type_in_terminal only submits on explicit consent, and file opens are confined to workspaces/vaults.
  • Repo allowlist consent is TOCTOU-safe. Consent is pinned to the file's SHA-1 and re-hashed at consent, boot, and sync. Better than almost every peer.
  • Main owns the command line. Renderer supplies only a vetted kind; custom agents are re-vetted on every read with inert, character-guarded args.
  • Audit log records actions, never payloads. The right call for a tool whose terminals may contain secrets.

Linux is network-contained, not file-confined

src-tauri/crates/tome-shim/src/linux.rs — TODO(landlock)

On macOS the seatbelt profile denies agent writes to userData and reads of the credential file. On Linux, bubblewrap + network namespaces block egress but there is no file-confinement layer yet — a network-contained agent can still read/write arbitrary files in the user's home. The README's "containment cell" framing overstates what Linux delivers today.

Action: implement Landlock (or a --tmpfs/bind-mount equivalent), or explicitly scope the Linux claim to "network isolation" until it lands.

The security docs describe code that no longer exists

SECURITY.md · docs/THREATMODEL.md · docs/perf.md

All three still describe the Electron build: src/main/, node-pty, electron-vite, electron-rebuild, "Electron userData", and a renderer "sandbox: true". After the Rust + Tauri rewrite none of those files or mechanisms exist (src/main/ is gone; PTYs live in src-tauri/src/pty.rs). For a security product, a threat model that points at the wrong code is worse than no doc at all — reviewers will chase ghosts and may skip the real code.

Action: re-verify every invariant against lock_gate.rs, authlock.rs, egress/, confine.rs, conductor/ and rewrite the three docs with correct paths.

SheetJS CDN pin

package.json · THREATMODEL invariant 7

xlsx is pinned to cdn.sheetjs.com with a lockfile integrity hash. It's documented and defensible (the vendor stopped publishing to npm), but it's a standing third-party distribution channel outside the registry.

Action: keep the pin; add a periodic re-verification of the integrity hash to the audit gate.

expert 02

🏗️ Software architect

Rating: 8.0 / 10 — clean boundaries, some very large files.

The split is sound: a dumb, confined renderer, a small shared/ layer for cross-boundary validation, and a Rust core that owns all authority (PTYs, proxies, fs, auth). That is exactly the right shape for a security-sensitive desktop app.

What's strong

  • Authority is in Rust (pty.rs, egress/, authlock.rs, fs.rs, lock_gate.rs); the renderer is a view + validated requests.
  • shared/ carries the validators (pane kinds, flow model, terminal text) so both sides agree without trusting each other.
  • Single-renderer pane grid (dockview + xterm) keeps the process model flat — a 6-pane workspace is not 6 browsers.
  • The flow subsystem (flow/) is self-contained and the runner keeps handoff files as plain markdown — debuggable and diffable.

Large modules invite drift

src/renderer/style.css (3.5k) · panels/flow.js (1.3k) · ipc/pty.rs (1.3k) · panes.js (1.0k)

Several files are >1k lines (with style.css at 3.5k). They're well-commented, but the pane/flow/pty modules are where most future change will land and where the layout-restore bug lived.

Action: as the flow and pane systems grow, extract narrow submodules with their own tests rather than extending the giants.

expert 03

🧪 Quality & release engineering

Rating: 6.0 / 10 — good unit coverage, thin integration story.

The unit-test floor is genuinely good, and the CI is unusually honest. The problem is the middle: nothing exercises the real renderer, and the Rust side isn't gated on the platform most of your users run.

What's strong

  • 282 vitest tests + 798 Rust #[test]s; lint and a renderer-bundle smoke check all gate on CI.
  • An audit gate (scripts/audit-gate.mjs) with reviewed, file-tracked exceptions instead of raw npm audit.
  • A dedicated linux-sandbox.yml that actually runs the #[ignore]d curl-matrix on real bwrap — rare and valuable honesty about what's unproven.

No macOS Rust gate in CI

.github/workflows/build.yml

build.yml (macOS) runs npm audit/lint/vitest/vite + a renderer smoke check, but never cargo test or cargo check. The seatbelt paths — the load-bearing macOS enforcement — are only exercised on a developer's laptop, while the Linux job tests a different sandbox on a different OS.

Action: add cargo test --lib (or at least cargo check) to build.yml; consider a macOS #[ignore]d seatbelt integration test like the Linux one.

macOS releases are unsigned and un-notarized

tauri.conf.json (signingIdentity: null) · release-tauri.yml

Releases default to ad-hoc signing. That's documented and roadmap'd, but for a security product the Gatekeeper quarantine warning is a real trust and adoption cost, and "verify the SHA256SUMS" is a poor substitute for stapled notarization.

Action: wire APPLE_CERTIFICATE/APPLE_API_KEY and add a spctl/stapler validate step to the release job.

Linux proof is a single point

.github/workflows/linux-sandbox.yml

Enforcement is proven on Ubuntu only. The AppArmor-userns (Ubuntu 24.04) case, Fedora, the self-unshare "rung 2" fallback, and Linux aarch64 are all uncovered.

Action: extend the matrix to Ubuntu 24.04 + Fedora, and add aarch64 Linux bundles.

No DOM/end-to-end test layer

test/ (logic-only) · src/renderer/panes.js

vitest runs with no DOM. A regression shipped where restoreLayout() was a silent no-op (it guarded on Array.isArray(saved.panels) while dockview stores an object), so panes never restored across restarts — and nothing in CI caught it.

Action: add a thin DOM harness smoke test for restoreLayout + pane spawn, or a Tauri WebDriver test that boots the app and asserts a layout round-trips.

Unmerged fix branch

git branch fix/restore-layout-and-poster

The layout-restore fix and the missing tour poster are committed on a local branch but not yet merged or runtime-verified in the packaged app.

Action: merge, then do one manual "save layout → relaunch → confirm panes restore" pass in the real app.

expert 04

⚡ Performance engineer

Rating: 7.0 / 10 — honest model, numbers not yet re-measured post-Tauri.

The resource model is right: one renderer, N pty processes, N proxy sockets — no per-pane browser overhead. The caveat is that the perf.md measurements (boot marks, bundle size, "node-pty rebuild") predate the Tauri rewrite and are no longer authoritative.

What's strong

  • Scrollback is capped (SCROLL_CAP 200k chars) and the event log is capped (5k records) — the two unbounded-growth vectors are bounded.
  • Lazy loading of mammoth/xlsx and the CodeMirror language table keeps cold-start work off the paint path.
  • The honest "measure it yourself" posture beats a fake headline number.

Perf numbers are stale

docs/perf.md

The boot table and "1.7 MB renderer bundle" figure are from the Electron build (electron-vite, node-pty, electron-rebuild). The Tauri renderer is bundled by Vite to dist-web/ and the backend is Rust — re-measure.

Action: re-run the TOME_PROFILE marks and re-print bundle sizes against the current build, and drop the node-pty postinstall note.

expert 05

📚 Documentation & consistency

Rating: 7.0 / 10 — excellent content, but internally inconsistent with the shipped code.

This repo writes docs the way it writes code: carefully. The README, interactive tour, launch guide, threat model and perf doc are all above-average. The problem is that the rewrite outran three of them.

What's strong

  • README is crisp and honest (unsigned builds, platform caveats, "voice is local").
  • The interactive tour is a genuinely good onboarding artifact.
  • The threat model is unusually precise about why each invariant is load-bearing.

Electron-era docs vs Tauri reality

SECURITY.md · THREATMODEL.md · perf.md

These are the same files the security expert flagged: they cite src/main/, node-pty, electron-vite, electron-rebuild and "Electron userData". None survive the rewrite. The threat model's file paths will send a future auditor to dead code.

Action: fold into the security-doc rewrite; add a doc-link check that fails CI when a referenced path no longer exists.

Version drift

package.json = 0.1.0 · README/docs = "v0.2.0"

The renderer package is still 0.1.0 while the UI and docs call it v0.2.0. There's no single source of truth (package.json vs Cargo.toml vs docs).

Action: bump to a real version and keep package.json/Cargo.toml/docs in lock-step in the release pipeline.
