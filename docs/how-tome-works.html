How Tome was made

An interactive tour of a desktop "coding harness" — an Electron app that puts AI agents, terminals, editors and a chat assistant in one tiled, sandboxed workspace. ~3,900 lines of JavaScript across three processes. Click everything.

1 · What it is

Tome is a desktop app that hosts other coding tools. Instead of alt-tabbing between a terminal running Claude Code, an editor, a PDF spec, and a chat window, Tome tiles them all in one grid — and wraps the AI agent terminals in a network sandbox so they can talk to their model provider but nowhere else.

The panes in the grid

The idea that makes it interesting: the chat assistant is a conductor. It can list panes, read a terminal's scrollback, type into terminals, and open files — so you can ask "what is claude doing in the other pane?" or "run the tests over there". Untrusted terminal output flows into the model, and the model's tool calls act on your machine — which is exactly why the security chapters below exist.

2 · Three processes, one trust boundary

Every Electron app is at least two programs: a Node.js "main" process with full OS powers, and a Chromium "renderer" that draws the UI. Tome's entire security design is one rule: the renderer holds no secrets and no powers. Everything dangerous lives in main; a tiny preload bridge decides exactly what the renderer may ask for.

4 · Security: the app assumes its own UI can be compromised

Tome runs AI agents that execute code — so it treats its own renderer and its own agents as potentially hostile. Four mechanisms do the heavy lifting:

The login gate wraps ipcMain.handle itself.

Every handler registered after the wrapper inherits the guard automatically — fail-closed by construction, not by per-handler discipline. Unlock is Touch ID or a scrypt-hashed passphrase, with optional TOTP second factor, plus exponential backoff on failures (5 misses → 30 s, doubling).

LOGIN SHELL SECRETS ARE ALLOWLISTED, NOT SCRAPED.

Agent CLIs spawned from a GUI app can't see keys exported in .zshrc, so Tome reads the login shell's environment once, async, at first agent spawn — but forwards only known provider keys (ANTHROPIC_API_KEY, OPENAI_API_KEY…). Your GITHUB_TOKEN never enters a sandboxed agent pane.

The auto-run guard strips control characters in main.

When "assistant may run commands" is off, the conductor's type-into-terminal tool strips CR, LF, Ctrl-C, Ctrl-D and ESC from model output — the model can type text but cannot submit it. Tab survives deliberately (completion text). The regex is pinned by tests.

Confinement everywhere a path crosses a boundary.

The brain vault, the tome:// protocol, the doc converter, and the conductor's open-file tool all resolve paths (including symlinks, via realpath) and refuse anything outside workspace folders. The TOTP secret is encrypted at rest with the OS keychain (Electron safeStorage).

These invariants used to live only in code comments; they're now collected in docs/THREATMODEL.md — written so a future refactor can't silently break an assumption three files away.

5 · The air gap, interactively

Agent panes spawn inside the macOS seatbelt sandbox (sandbox-exec) with all direct network egress denied — DNS included. The only way out is a per-pane loopback proxy that allows model-provider domains only. Unlocking a pane widens the proxy, never the sandbox — there's no code path that weakens the sandbox after spawn, so there's nothing to forget to re-harden.

Wildcard anchoring matters: the allowlist entry bedrock-runtime.*.amazonaws.com must match …us-east-1.amazonaws.com but reject ….amazonaws.com.evil.com. Tome compiles wildcards to anchored regexes — and the test suite pins the evil.com case so nobody "simplifies" it into a suffix match later.

6 · Crypto lab: the authenticator code, by hand

Tome's second factor is TOTP — the 6-digit code in your authenticator app. It's HOTP (RFC 4226) where the "counter" is the current 30-second time step (RFC 6238). Tome implements it by hand in ~40 lines — and pins it against all ten RFC test vectors. This is the real algorithm, running in your browser right now:

6.1HOTP(secret, counter) = truncate(HMAC-SHA1(secret, counter))

secret = "12345678901234567890" · counter = 0
······

Counters 0–9 against the RFC's published vectors: 755224, 287082, 359152, 969429, 338314, 254676, 287922, 162583, 399871, 520489. Step through them and watch each one verify. ✓

the actual implementation — src/main/lib/totp.js
export function hotp(secret, counter) {
  const buf = Buffer.alloc(8)
  buf.writeBigUInt64BE(BigInt(counter))        // counter as 8 bytes, big-endian
  const h = createHmac('sha1', secret).update(buf).digest()
  const o = h[19] & 0xf                          // last nibble picks the offset…
  return String((h.readUInt32BE(o) & 0x7fffffff) % 1e6).padStart(6, '0')
}                                                   // …dynamic truncation → 6 digits
The passphrase side uses scrypt (memory-hard, so brute force is expensive) with timingSafeEqual for comparison (no timing side-channel). The base32 encoder is hand-rolled too — and round-trip-tested, because hand-rolled crypto without pinned tests is a coin flip.

7 · The conductor: a model with its hands on the grid

The chat pane is not a bolted-on chatbot — it's a conductor with five tools: list_panes, read_terminal, type_in_terminal, open_pane, open_file. The model runs in a bounded tool loop: it replies, calls tools, reads the results, replies again — up to 8 turns per message, with a 400k cumulative token budget and a stop button wired to an AbortController.

The confused-deputy loop, named: the conductor reads terminal scrollback (untrusted — a repo's build script can print anything) and the model's tool calls act on your filesystem. Hostile output can steer the model. That's why the guards live in main, not in the prompt: open_file is confined to workspace folders, and type_in_terminal can't submit unless you flip the auto-run toggle.

the guard, verbatim — src/main/conductor.js
// With auto-run off the text must stay un-submitted, so strip the control
// chars that would submit or signal on their own (CR/LF, Ctrl-C, Ctrl-D…).
// Otherwise `text: "ls\r"` runs a command the user never approved.
const text = allowRun ? String(input.text) : stripControlChars(input.text)
p.write(text + (enter ? '\r' : ''))  // enter only exists when allowRun is on
Each tool turn re-sends the whole transcript, so 8 turns at max_tokens: 64000 is a worst-case ~1M output tokens for one user message. The cumulative budget check runs between turns (usage only exists per completed turn) and ends the loop gracefully with a visible note instead of a surprise bill.

A broken renderer import fails here, in CI — not at runtime on a user's machine. The smoke check parses every emitted bundle with node --check.

9 · Layout persistence: the grid remembers

dockview serializes its whole grid with toJSON() — panel ids, titles, params, positions. Tome saves that blob per workspace (debounced on every layout change, and once more on quit via a main-process handshake) and restores it on reopen. The store key is derived from the workspace's folder list, so renaming a workspace keeps its layout.

9.1Play with a miniature grid

The one pane that can't come back: a terminal is a live OS process — its scrollback and running programs die with it. On restore, Tome recreates each terminal/agent pane as a fresh shell in its saved position (same kind, cwd, air-gap state). Editors, docs, chat and brain panes restore for real. Stale entries — deleted files, removed workspaces, panels from older builds — are skipped silently instead of breaking the whole restore.
